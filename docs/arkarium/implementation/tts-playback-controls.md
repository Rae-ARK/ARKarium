# TTS playback controls (pause/resume, skip, controls bar)

> **Kind:** implementation (ladder) · **Status:** rungs 1-5 done (5 awaiting an on-device check), rung 6 current · **Verified:** 2026-11-08
> **Truth lives in:** `playback/TtsPlaybackService.kt`, `playback/TtsNotificationActions.kt`, `ui/Tts.kt`, `ui/ReaderScreen.kt`, `ui/ReaderTtsLogic.kt`, `ui/WaterRipple.kt`

Promoted from [`../proposal/uiux.md`](../proposal/uiux.md)'s "Read-aloud has no
playback controls and no 'currently reading' highlight" entry, now deleted from
that file - see this doc's history (or `git log -p` on that line) for the
original writeup. Builds on `TtsPlaybackService`
([`reader-playback.md`](../proposal/reader-playback.md) F10), which already keeps a
read-aloud session alive across rotation and chapter navigation - this ladder
is the "controls surface" that doc's "Still open" section flagged as not built
yet.

## Ladder

| Rung | State | What |
|---|---|---|
| 0 | done | Design doc (this one). |
| 1 | done | `TtsPlaybackService`: `pause()`/`resume()`/`skipNext()`/`skipPrevious()`, chunk granularity. Pause is modeled as "stop, remember `pendingIndex`, resume from that chunk" (not a real `TextToSpeech` feature); skip jumps `pendingIndex` directly and only re-queues speech if something was actually playing. `ChapterTtsState` (`ui/Tts.kt`) mirrors a new `isPaused` and passes all four calls through. |
| 2 | done | Reader UI (`ReaderScreen.kt`). The top-bar speaker glyph (`Icons.Filled.VolumeUp`, shown outside immersive mode only) starts read-aloud (a paused session resumes, a playing one is left alone) and enters immersive mode. The bottom edge is one slot that swaps: outside immersive mode the "Reader Preferences" pill, in immersive mode - while a session exists, playing or paused - `TtsControlsBar` (stop, settings, skip back, play/pause, skip forward); `readerBottomPill` (`ReaderTtsLogic.kt`) decides which. The swap plays a water ripple (`WaterRipple.kt`: a circular reveal plus expanding rings). Close (X) stops the session, which removes the pill; the gear opens `settings/tts` via `onOpenTtsSettings`. |
| 2a | done | The session lives in `TtsPlaybackService`, so it outlives the reader screen. `showControls` (the immersive flag) is `rememberSaveable`, and once the service re-binds, `reconcileTtsSession` handles a session already running: reading this chapter, it returns the reader to immersive mode so the pill is back (covers returning from `settings/tts`, rotation, reopening the chapter); reading another chapter, it is stopped as stale (Previous/Next). `TtsPlaybackService.sessionKey` - the chapter id passed to `ChapterTtsState.speak()` - is how the two are told apart. |
| 3 | done | Chunk-level progress indicator inside `TtsControlsBar`. Ships the simpler of the two options "Rung 3" below laid out: `chunk N of M`, not a page estimate (that option is left for whenever F9's character-offset anchor is wired to the TTS chunk index, which it isn't yet - see `reader-playback.md` F9). `TtsPlaybackService.pendingIndex`/`pendingChunks` are exposed as `currentChunkIndex`/`totalChunks`, pushed through a new `Listener.onChunkProgressChanged(index, total)` the same way `isSpeaking`/`isPaused` already push; `ChapterTtsState` mirrors both. `ttsChunkProgressLabel()` (`ReaderTtsLogic.kt`) is the plain-Kotlin, unit-tested (`ReaderTtsLogicTest.kt`) 0-based-to-1-based-and-clamp logic; `TtsProgressIndicator` (`ReaderScreen.kt`, replacing the old `TtsProgressStub()`) renders it, or nothing with no session. |
| 4 | done in code - on-device check open | Media-notification transport actions on the foreground notification: previous, play/pause (one slot that swaps), next, stop, in `androidx.media`'s `MediaStyle` with the first three kept in the collapsed view. Adds the `androidx.media:media` dependency (`app/build.gradle.kts`). The existing framework `MediaSession` (F22) is kept - its token is wrapped with `MediaSessionCompat.Token.fromToken` rather than the session being rewritten on `MediaSessionCompat`, so there is still one session. Each button is a `PendingIntent.getService` carrying one of `TtsTransportAction`'s intent actions; `TtsPlaybackService.onStartCommand` routes it to the same `pause()`/`resume()`/`skipNext()`/`skipPrevious()`/`stop()` rung 1 added (a tap with no live session just stops the service). The notification is re-posted from `updateMediaSession()` so the play/pause button follows state, and only while a session is live. The which-buttons/what-does-a-tap-mean decisions are plain Kotlin in `playback/TtsNotificationActions.kt` with `TtsNotificationActionsTest`. Not yet built or run on a device. |
| 5 | done in code - on-device check open | Chunk-level "currently reading" highlight + auto-scroll. The chunk-index → text-range mapping was *not* quite free: `splitForTts` returned only strings, so `splitForTtsSpans` (`TtsPlaybackService.kt`) now returns each chunk's `[start, end)` in the original chapter body, and `splitForTts` is just those spans sliced back to text (`SplitForTtsTest` still pins its behavior). The service keeps the spans beside `pendingChunks` and exposes `chunkSpan(index)`; `ChapterTtsState` mirrors the current chunk's range as `currentChunkStart`/`currentChunkEnd` (-1 with no session), pushed with `onChunkProgressChanged`. In `ReaderScreen` the range is drawn as a background span (`textColor` at 16% alpha, so it suits every reading mode) *inside* the existing text block: the reader renders everything between markup tags as one `Text`, usually the whole chapter, so shading whole blocks would shade the entire chapter; `ttsHighlightWithin` clips the chunk to each block. Auto-scroll runs when the chunk changes: `ttsBlockForChunkStart` finds the block, its `TextLayoutResult` gives the chunk's first line, and `ttsAutoScrollTarget` leaves a tenth of the viewport above it (skipping the nudge when it is already about there). Chunk-level only - it never fights a reader scrolling mid-chunk; the next chunk brings them back. Both wait for `reconcileTtsSession` to have run, so a stale session can't shade or scroll another chapter. Not covered: a chunk starting inside an `<author>`/`<news>` callout or divider (drawn as separate widgets, so nothing is shaded and the scroll stays put). Chunks run up to 3800 characters, so the shaded region is large; rung 6 narrows it. Not yet built or run on a device. |
| **6** | **current** | Word-level highlight enhancement via `UtteranceProgressListener.onRangeStart` (API 26+; `minSdk` is 24, so rung 5's chunk-level version stays as the fallback branch, not replaced). |
